# October 2026 fixes: what changed and how to deploy

## Run the SQL first
Run `scripts/sql/002_payment_idempotency.sql` in the Supabase SQL editor
(Dashboard > SQL Editor > New query > paste > Run) BEFORE deploying the code.
It is additive and idempotent: one nullable column `payments.idempotency_key`
and a partial unique index. It drops and rewrites nothing, so existing rows stay valid.
`001_bill_receipt.sql` is NOT needed: the receipt is computed from existing columns.

## Duplicate-payment protection
1. UI: `SubmitOnceButton` disables while a server action is pending.
2. Server: bill row lock + already-paid check (existing).
3. Server: per-form idempotency key; a repeat returns the stored payment.
4. DB: unique index on (restaurant_id, idempotency_key) and on lower(transaction_id).

## Refresh intervals
`LiveRefresh` (router.refresh, paused while the tab is hidden, refresh on return):
orders/kitchen/tables 3-5s; billing, payments, loyalty, offers 10s; bell polls 30s.
Money pages use 10s to limit database load; they are not a live board.

## Loyalty: decisions needed before building
- Points earned per rupee, and rounding
- Redemption thresholds; discount type (percent/fixed) and caps
- Point expiry
- Eligible bills/items; do offers stack with discounts?
- Is a mobile number entered once per visit or per bill? OTP verification?
- Consent/privacy wording for storing phone numbers
Existing code has three overlapping loyalty/offer implementations
(`modules/loyalty`, `modules/financial-pots`, `modules/offers`); pick one first.
